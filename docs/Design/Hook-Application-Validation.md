# Hook transition: application and warning validation

Date: 2026-09-30. The composed application fixtures, warning-policy checks,
controlled traffic run, and corrected Swagger test fixture all passed on
Linux/Node 24.21.0. Fastify's production code remains the previously tested
candidate; this work adds validation scripts, results, and a plugin test patch.

These were constructed applications using real released plugins. No user
application repository, deployed staging environment, or private warning
configuration was supplied. The results therefore provide additional release
evidence without replacing a deployment trial in an actual application.

## Application smoke checks

Each build ran three application profiles: legacy signatures with an optional
feature enabled, legacy signatures with it disabled, and corrected signatures
with it enabled. The application combines an authenticated JSON API with an
upload/WebSocket gateway.

The checks verified JWT authentication, signed cookies, CORS, schema errors,
POST payload transformation, callback hook arrays, GET/HEAD equivalence,
autoloaded nested routes, hooks generated by `onRoute`, conditional plugin
loading, OpenAPI document generation, multipart uploads, and WebSocket echo.

Every profile also performed 20 real TCP upload aborts and 50 WebSocket
messages. Per-request markers detected duplicate hook/handler execution.
There were no duplicates, cleanup errors, or unexpected server error logs.

The candidate emitted 13 registration warnings in the enabled legacy profile
and 11 in the disabled profile. Corrected profiles and the baseline emitted
none. Counts did not increase during requests. Candidate enabled profiles used
zero-argument async abort hooks inside route arrays; all cleanup checks passed.

## Warning handling and startup volume

Each build passed 23 warning/startup scenarios, including intentional failures
under strict application policies. For the 20-GET-route legacy fixture:

| Policy | Candidate result |
| --- | --- |
| Default Node output | Boots and serves requests; 40 warnings |
| Structured warning logging | Boots and serves requests; 40 warnings |
| Throw on every warning | Exits with code 1, as that policy requires |
| Log `FSTDEP023`, throw on other warnings | Boots and serves requests |
| Explicit CI failure on `FSTDEP023` | Completes boot/request checks and exits 1 |
| Node `--throw-deprecation` | Boots and serves requests |

Correcting the signatures removed the warnings and passed every policy.
These results confirm that an application's own fatal warning listener can
still block this transition. Update that existing policy deliberately or fix
the signatures before rollout. Adding a second listener does not prevent an
existing listener from throwing.

Startup measurements below are medians of three fresh child processes. Each
GET also registers HEAD. Warning events were delivered to a structured logger
and Node's default stderr output was captured.

| GET routes | Signature | Baseline boot | Candidate boot | Candidate warnings | Candidate stderr |
| --- | --- | --- | --- | --- | --- |
| 500 | Legacy | 134.19 ms | 174.20 ms | 1,000 | 400,352 bytes |
| 500 | Corrected | 134.48 ms | 134.72 ms | 0 | 0 bytes |
| 2,000 | Legacy | 375.58 ms | 523.93 ms | 4,000 | 1,603,852 bytes |
| 2,000 | Corrected | 373.49 ms | 396.01 ms | 0 | 0 bytes |

For 2,000 affected GET routes, warning output added about 148 ms to measured
startup versus the baseline and produced 1.60 MB on stderr alone. Structured
logging produces additional output. This is a concrete rollout consideration
for applications with many affected routes. The capture sink does not model a
slow remote logging service; check the deployment's actual log collector and
readiness budget. No warnings were emitted per request.

## Controlled traffic and cleanup

Each build ran three 20-second rounds after warmup, with 25 HTTP connections.
Traffic alternated authenticated GETs and JSON POSTs while each round also
performed 100 deliberate upload aborts and 500 WebSocket messages. The server
and load generator ran in separate processes on the same Linux runner.

| Measurement | Baseline | Candidate |
| --- | --- | --- |
| Measured HTTP requests | 472,392 | 464,901 |
| Requests/second over measured durations | 7,870.58 | 7,747.06 |
| HTTP p99 latency, each round | 9 ms | 9 ms |
| Transport errors / timeouts / unexpected statuses | 0 / 0 / 0 | 0 / 0 / 0 |
| Deliberate upload aborts / route cleanup calls | 300 / 300 | 300 / 300 |
| WebSocket messages | 1,500 | 1,500 |
| Duplicate hook/handler executions | 0 | 0 |
| Heap after first / last round, after GC | 15.57 / 15.67 MiB | 15.64 / 15.74 MiB |
| Tracked uploads / sockets / WebSockets after shutdown | 0 / 0 / 0 | 0 / 0 / 0 |

The candidate's aggregate throughput was about 1.6% lower in this run.
This short sequential comparison is descriptive, not enough to establish a
performance regression or production capacity. Heap samples and tracked
resources showed similar behavior; all child servers exited normally. This
does not substitute for a long-duration soak or prove absence of memory leaks.

## Swagger compatibility correction

The prior failure came from a Swagger test assuming that Fastify enables
`QUERY` by default. The existing public `addHttpMethod` API can register it on
this Fastify version. The [test-only patch](swagger-query-compatibility.patch)
adds this line to that test's setup:

```js
fastify.addHttpMethod('QUERY', { hasBody: true })
```

The HTTP method's request-body and OpenAPI assertions remain enabled. There
are no skips and no change to Fastify's default HTTP methods.

Both baseline and candidate passed Swagger lint, all 298 runtime tests,
100% coverage, and all 11 TypeScript assertions across five files. The source
revision was pinned to `f3ecd6365bd39da545b1537daa5b1956a09368ce`, matching
the original failing plugin run.

This supplies a tested correction for the compatibility exception. The patch
has not been submitted or merged upstream, and the historical unmodified
plugin run remains red. Maintainers still need to adopt the correction or
otherwise align the test with the target Fastify version.

## Remaining limits

The four requested areas have been exercised as far as the available fixture
environment permits. Actual application configuration, external services,
remote logging behavior, deployment readiness checks, and longer staging
traffic remain application-owner validation. Strict hook enforcement remains
future major-release work. No release or upstream merge was performed.
